# Pioneer C — 实时预览可行性原型

**问题**：冻结的宣传片管线（`promo/` + Echo Render 算子）能不能被一个正在跑的任务的中间产物**增量驱动**，快到坐在屏幕前的人能看着场景一点点长出来？

## 判定：成 ✅

按事先定死的规则（真实数据规模下、重阶段每次可见更新 ≤2 秒）：**全部阶段、全部数据规模下都达标，且有余量。** 最重的一次更新（满屋 208,666 点已膨大成实体 + 一张整幅照片正贴在墙上）中位 0.78 秒，最差单次实测 1.19 秒，仍在 2 秒线内。这台 VM 是 4 核无显卡的弱机，用户自己的电脑只会更快。不需要抽稀；抽稀方案也测了（见表末），留作更弱机器的保险。

## 做法

`live_driver.py`（与本文同目录）把 room2 任务的真实中间产物按管线顺序“回放成在陆续到达”，每到达一批就用算子在 **1280×720 原生分辨率**下渲一次可见更新，并计时（备料 / 算子 / 实体层 / 总计）：

- **抽帧**：230 张真彩照片卡陆续在空间里出现（promo v3 的卡片资产，亮色、羽化边）；
- **位姿**：拍摄路线在全局底特律蓝格里逐笔描出；
- **深度**：229 帧逐帧到达——整幅照片先贴上它面对的墙（v3 全幅照片资产，163k 采样点），随即按**已批准的压碎数学原样**碎成点、落回真实位置（`start + delta·p² + burst·sin(π·p^0.7)`，一字未改）；
- **融合**：落位的点按 v3 规则在 1.5 秒内膨大成实体块（节距 0.11），最后镜头拉远成整屋实体。

外观全部复用冻结代码：全局格 + 散线、亮照片、压碎粒子、膨大实体层（`batch_lib3._solid_composite` 原函数）。原型只做了两件新事：把冻结的“按节拍编排”换成“按到达顺序驱动”，以及一台沿路线走的直播镜头。

读表要点：

- **算子本身从来不是瓶颈**（11–380 ms）；时间主要花在**实体层**（落位点越多越大，≥100k 点后占 0.4–0.7 秒）——但满负荷也只到 ~0.8 秒。
- 膨大系数按最坏情况测的：已落位点全部取 g=1（完全长成）。直播早期点还在长，实际只会更快。
- **冷启动第一帧 4.5 秒**（一次性：数值内核首次调度 + 缓冲建立；内核有磁盘缓存）。产品里把这帧藏在抽帧阶段开始前预热即可，不影响任何阶段的节拍。
- 备料（numpy 切片/变色）基本可忽略；只有 230 张卡全在场那次到 0.13–0.2 秒量级。

## 和真实管线的速度关系（重要）

渲染侧不是瓶颈后，直播的实际节拍由**管线自己产出中间产物的速度**决定。room2 那次真实运行里，深度阶段约 12 分钟产出 230 帧 ≈ **每 3.1 秒一帧**——比渲染更新（≤0.93 秒）还慢。也就是说在同等机器上，画面永远等数据、不会被数据追着跑；用户电脑上两边一起变快，关系不变。抽帧和位姿阶段产物到达更快，但那两段的更新成本也最低（≤0.51 秒 / ≤0.01 秒）。

## 演示视频

`live_preview_demo.mp4`（同目录，54.6 秒，720p30，静音，码率按发布规则封顶 5M，全片解码校验通过）：把上面整条模拟直播录了下来——卡片到达 → 路线描出 → 229 帧逐帧贴墙压碎落位 → 膨大成实体 → 拉远收尾，带阶段字幕。**播放节奏是压缩过的示意**（真实运行里深度阶段每帧要等约 3 秒），节拍结论以上面的实测表为准，不要拿视频时长反推。

一眼能看出的毛病（诚实记录）：深度阶段中段有几秒画面偏空——那几秒镜头正走到拍摄者穿出房门的那段路线上，已建成的部分在镜头背后、前方是还没建的空间。这是数据本身（路线确实中途出过房门），不是渲染问题；产品化时直播镜头要专门设计（比如贴墙事件时切到该照片的观看位），那属于镜头编排，不影响本实验的节拍结论。

## 边界与剩余工作

- 本原型是**回放模拟**：消费的是管线已经写盘的同一种中间产物（帧、位姿、逐帧深度落点 + 溯源 sidecar、融合点云）。证明的是“增量驱动 + 渲染节拍”成立；产品化还差一个**盯任务文件夹的驱动钩子**（新文件落盘 → 喂给这个驱动 → 画面进 app 中部），渲染路径本身不用再改。
- 相机在原型里是简单的沿路线行进；用户幻想里的“照片贴墙时推近特写”需要一遍直播镜头编排（参考宣传片 v3 的分段保持逻辑），属于设计工作、不是性能问题。
- 内存：满规模一次更新的峰值在本机可控（资产约 0.7 GB 常驻 + 每帧临时缓冲几十 MB），与 app 同进程共存没问题。
