# 先锋 G 报告：第三条发现路线（模型提名）实测

**问题**：现成的开放词汇检测模型在本机 CPU 上，能不能在用户真实房间帧里
**提名**出已证的锚（86 面板 / 门 / 笔记本屏幕）和大家具——喂给
「提名 → 测量裁决」架构当提名器？

**方法**：google/owlv2-base-patch16-ensemble（transformers 管线，CPU，
阈值 0.10），room2 六帧（00310 / 00180 / 00194 / 00016 / 00040 / 00057），
查询词：electrical outlet panel / power socket / door / laptop screen /
laptop / bed / desk / bookshelf / book / bottle / chair。
判定线开跑前写死在 run_detection.py 里。Muse 逐帧看标注图核对框的位置。

## 误报与毛边（如实记）

- frame_00057 的 door 0.378 框中的是**柜门**，不是房门——测量裁决按门宽
  候选集量它会否决，但提名器分不清房门与柜门。
- frame_00310 的「bottle」框中的是椰子脆块的**罐子**——形状近似的误提名，
  裁决层拒收即可（本来也不在锚目录里）。
- bookshelf 有几框框得松（把书堆/桌面一起框进去）——只够提名，不够定位，
  定位仍归测量层。
- 分数整体不高（锚 0.31–0.65）：阈值必须放低（0.10–0.15），靠裁决层过滤，
  不能靠分数一刀切。

## 成本

本机（4 vCPU 无 GPU）：**每帧 269–295 秒**。六帧共约 28 分钟。
产品化不能在本机这种速度上全帧跑；可行形态：只跑挑选后的清晰帧
（一次作业约百帧量级仍偏重），或在用户 PC 上跑，或换更小的同类模型。
这是部署问题，不影响「提名能力成立」的结论。

## 结论与接法

- **提名器成立**：程序发现的第三条路线（模型提名）通过预设判定线。
  强发现自此有两条提名腿：几何发现（已随真尺度 v1 上线）+ 模型提名（本测）。
- 接入顺序不变：提名 → 现有测量链裁决 → 过了才进物品清单 / 定尺锚。
  模型永远只有提名权，没有裁决权（与深度模型同笼）。
- 直接收益：真尺度 v2 缺的**门、笔记本屏幕提名**补上了；
  物品清单（先锋 F）可以从「Muse 肉眼看帧」升级为程序自动提名。
- 本次六帧 + 已知锚位置可作验证集种子，日后换模型/调阈值拿它回归。
