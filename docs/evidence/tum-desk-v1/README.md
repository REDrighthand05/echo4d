# ECHO4D｜第二段真实录像的两次验证

**我们想确认什么？** 上次 ECHO 能从一段较简单的影像计算相机如何移动。这次换成办公室桌面较多、转动更多的另一段真实拍摄资料，看看是否仍能找到拍摄路线。

- 研究档案：[GitHub Issue #20](https://github.com/REDrighthand05/echo4d/issues/20)
- 实际代码：[Draft PR #21](https://github.com/REDrighthand05/echo4d/pull/21)
- 第一次真实运行：[Actions #40203647194](https://github.com/REDrighthand05/echo4d/actions/runs/40203647194)；第二次从零核验：[Actions #40204111307](https://github.com/REDrighthand05/echo4d/actions/runs/40204111307)

### 为什么要看第二次？

电脑第一次从 TUM 的官方 HTTPS 服务器下载了 344,011,403 字节，得到SHA-256：`e983d6830916e66dc4a46a71368046b149b283de87769690e7aa4e0b9483530c`。这不是 TUM 官方签名，而是我们**第一次从官方源实测**的内容指纹；第二次在运行计算前重新下载并强制验证，确认是完全相同的数据。两次的测试视频文件指纹也完全一致。

代码依次自己提取画面特点、匹配共同物体、推算相机位置。我们只让定位计算读到彩色画面和已知相机内参。**完成计算以后**才打开官方的实际相机路线进行比较。

两次结果很接近但不完全相同：空间特征点相差 9 个，路线平均偏差指标分别约为 2.60 与 2.50 厘米。这个数字采用**同一批照片的最佳对齐**，是相机路线形状的回顾式评分，不能理解为 ECHO 已经从普通视频知道真实的物理厘米数。

## 重要限制（不能删）

1. 使用真实摄像头 RGB 帧**重新编码**为视频，不是原生手机录制的 MP4；以4帧/秒重新安排时间轴。
2. 已知相机的镜头参数，而且两个已完成的TUM场景使用同一相机系列；**尚未验证跨设备泛化**。
3. 单靠彩色视频仍然**不知道物体的实际尺寸**；没有额外测距时输出 `units=unknown`。
4. 只恢复少量特征点和相机轨迹，**不等于已经恢复完整房间、墙面或桌面形状**。
5. 两次求解结果数值接近，但轨迹文件哈希不同，不能声称逐字节相同。所有失败和未注册画面必须可审计。

## 证据清单

- `first/report.json` 与 `repeat/report.json`：两次机器记录，包括命令、真实下载、按画面报告的偏差和时间。
- `first/trajectory-scale-unknown.json` 与 `repeat/trajectory-scale-unknown.json`：两次由COLMAP实际计算的75个相机位置（单位仍未知）。
- `first/zip-file-checksums.json`、`repeat/zip-file-checksums.json`：两次Actions ZIP内所有文件哈希，包括体积较大的实际特征匹配文件。
- `comparison.json`：由原始报告独立重算并核对的可机读对照。
- 大型 `images.txt`、`points3D.txt` 保留于上述两个Actions页面的Artifacts中；这些短期附件可能过期。
